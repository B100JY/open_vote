# 경량 감사 v1 구현 기록·운영 전 준비

- 대상: [v1.0 계획](voting-native-audit-plan-2026-10-28.md)
- 위치: `open_vote`, `fix/vote-receipt-guidance`. 기존 미커밋 통합·디자인 작업을 보존했다.
- 상태: 사용자 요청으로 2026-10-28 운영 DB 적용·배포 완료. [배포 기록](deployment-2026-10-28-native-audit.md) 참조. 실제 문자·커밋·푸시는 수행하지 않았다. 아래 운영 전 준비·초기 검증 항목은 구현 시점 기록이며, 후속 적용 결과는 배포 기록이 우선한다.

## 구현 범위

- 기존 접수/과금을 유지하고 감사 선거만 새 경로를 사용한다. 기존 선거는 `audit_version=0`이며 자동 변환하지 않는다.
- 생성 화면의 ‘서명 확인증·공개 감사’와 선택형 ‘제출 전 휴대폰 문자 인증’을 제공한다. 감사 서명키가 없으면 감사 선거 생성은 과금 전에 중단한다.
- 감사 선거 생성·명부·과금·규칙 고정은 `audit_create_billed` 하나의 DB 트랜잭션으로 처리한다. 감사 설정 이후 명부 연락처·투표 규칙은 고정한다. 토큰 회전·참여 표시·상태 변경은 허용한다.
- 표/명부에는 시각·순번/신원 연결을 새로 넣지 않고, 별도 체인에는 숨김 약정만 넣는다. SQL/JS 해시를 교차 검사했다. 정규화 입력은 감사 스키마의 ASCII 필드명과 제한된 정수/집계 수치로 제한한다.
- 접수·1회 소비·약정 이벤트·마감 이력을 같은 확정 경계에서 처리한다. 레거시 내부 기표/직접 INSERT의 감사 우회도 트리거로 거부한다.
- 확정 자료만 P-256/SHA-256으로 서명하고 최초 저장한 서명을 재사용한다. 서명 개인키는 DB에 넣지 않는다.
- 시작 고정본·진행 중 서명 기준점·마감 공개 묶음을 저장할 수 있다. 공개 조회에는 salt/k/신원/영수증 해시-체인 연결을 넣지 않는다.
- 제출 전 로컬 pending 확인증을 저장하고 응답 유실 뒤 같은 약정으로 조회한다. 이미 투표한 안내에서도 같은 탭에 남은 pending 파일의 접수 서명을 이어받을 수 있다. 본인 문자 인증으로 개인 표를 찾아주는 연결 표는 만들지 않는다.
- 네 방식의 별도 집계기와 항목별 보고서, 오프라인 HTML 검증기와 Node CLI를 제공한다. 외부 시작 규칙·서명 기준점 사본과 비교할 수 있다.
- 일반 관리자 접근 제한과 운영자/원시 DB 접근자의 잔여 위험을 안내에서 구분한다.

- [키 생성 도구](../scripts/create-audit-key.mjs): 저장소 밖의 새 절대경로에만 쓰며 비밀을 출력하지 않는다. 이번 구현에서는 실제 운영 키를 생성하지 않았다.

```text
npm run audit:build
node scripts/verify-audit.mjs 공개묶음.json [개인확인증.json] [시작규칙또는기준점.json]
node scripts/test-native-audit-db.mjs
```

DB 시험은 환경변수의 운영 연결을 사용하지 않는다. OS 임시 폴더에 새 PostgreSQL 클러스터를 만들고 loopback 임시 포트에서만 합성 데이터를 사용하며 종료 때 자신이 만든 서버만 중지한다. 기본 바이너리 경로는 Windows PostgreSQL 17이고 필요하면 `PG_TEST_BIN`으로 지정한다. 시험 폴더에는 합성 공개 자료와 DB만 남는다.

오프라인 검증기는 `public/audit-verifier.html`이며 빌드 때 생성한다. 개인 확인증(JSON), 공개 묶음, 선택적인 독립 시작 사본/기준점을 선택해 검사한다. CSP의 `connect-src 'none'`으로 외부 통신을 차단한다. 기존 HTML 영수증은 기존 검증 방식으로 호환한다. 서명 확인증은 JSON으로 저장한다.

API:

- `POST /api/elections`의 `enableAudit`, `smsRequired` 설정(관리자/생성자 권한).
- `POST /api/elections/{id}/audit`: 관리 권한으로 표가 없는 선거의 설정을 고정하고 서명 규칙 반환. 기존 감사 선거는 고정 설정을 그대로 반환한다.
- `GET /api/elections/{id}/audit?manifest=1`: 시작 고정본.
- `GET /api/elections/{id}/audit?checkpoint=1`: 현재 서명 기준점.
- `GET /api/elections/{id}/audit?commitment={c}`: 공개 이벤트/접수 서명만 조회. c는 소유 증명이 아니다.
- `GET /api/elections/{id}/audit?bundle=1`: 마감 후 묶음과 항목별 보고서.
- `POST /api/vote/audit`, `POST /api/vote/otp`: 링크/코드/로그인 자격 경계를 함께 사용한다. 전화번호만으로 자격을 찾지 않는다.

기존 외부 v1 연동의 선거 생성 형식은 유지한다. 그 경로에서 감사 사용을 자동 가정하지 않는다. 감사로 설정된 선거에 레거시 기표를 제출하면 DB가 거부하므로 새 감사 제출 규격을 사용해야 한다.

## 운영 전 필수 준비

1. 마이그레이션은 공유 프로젝트 `app_open_vote` 범위에서 별도 승인 후 적용한다. `db push/repair/pull`은 사용하지 않는다. 새 표는 RLS·서비스롤 권한만 가지며 함수의 PUBLIC EXECUTE를 회수하고 기준선 검사를 수행한다.
2. `MOAI_AUDIT_PRIVATE_JWK`를 비밀 환경변수에 등록하고 DB/공개 자료 백업과 분리해 보관한다. 키를 교체하면 진행 중 선거의 고정 키를 자동 대체하지 못하므로 기존 키의 사용·복구 절차를 먼저 정한다.
3. OTP 실발송을 사용하려면 코드만 담는 사전 등록 템플릿과 `MOAI_OTP_TEMPLATE`, `MOAI_OTP_SEND_ENABLED=true`, 기존 notifier 서버 설정이 필요하다. 발송 활성화 자체가 실제 문자 수신·제공자 로그 시험을 대신하지 않는다.
4. OTP는 6자리·5분, 승인 5분, 번호별 재발송 60초, 오입력 누적 5회·발송 5회, 선거 전체 정원×3회 한도다. 현재 정책은 발송당 1P다. 제공자가 명확히 실패를 반환하면 한 번만 환불하며, 타임아웃처럼 발송 여부가 불명확하면 자동 재발송·환불하지 않고 정산 대상으로 남긴다. 이 제한·비용·실패 안내를 운영 전에 확인한다.
5. 실제 Supabase 전체 이력·운영 스키마와의 적용, 실제 브라우저/휴대폰·수신·과금·제공자 로그, 저사양 모바일 대규모 성능, 실제 키 백업 복구·외부 사본 배포는 미검증이다. 합성 DB 시험을 그 결과로 대신 보고하지 않는다.
6. 설치 시 `npm audit`는 기존 Next.js 등 의존성의 취약점을 보고했다. 감사 기능의 검증과 별개로 운영 배포 전에 의존성 보안 업데이트를 검토한다. 관련 없는 패키지를 이번 작업에서 일괄 갱신하지 않았다.

## 보장 한계

실제 적격자의 의사·운영자 유령 표·악성 웹 JS·사적 열람 부재는 증명하지 않는다. 약정 전체와 공개 평문 표 전체의 대응도 증명하지 않는다. 외부 사본 없이 서버 자료만 대조한 경우 최초 독립 확인 완료로 표시하지 않는다. 서명 충돌은 발급 자료 간 모순의 증거이며 고의 부정의 원인을 자동 판정하지 않는다.

- 수정한 tracked 소스/패키지의 `git diff --check`: 통과. 전체 워크트리에는 작업 전부터 있던 dev 로그의 EOF 공백이 있어 관련 없는 로그를 지우거나 고치지 않았다.
- 형식/기술 참고는 표준 Web Crypto·RFC 8785와 설치된 Next.js 16 문서를 읽었으며 Supabase/잠금 순서/React 스킬 기준을 점검했다. 자체 암호 원시 연산은 구현하지 않았다.
