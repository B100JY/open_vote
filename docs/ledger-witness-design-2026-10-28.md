### v0.7 실행 방향

다음 단계는 자체 암호 구현이 아니라 [기존 투표 엔진의 격리 실험 계획](ledger-witness-poc-plan-2026-10-28.md)이다. **현재는 공식 자료 확인과 계획 작성만 했고 설치·PoC 실행은 하지 않았다.**

- Belenios를 우선 평가 후보로 삼는다. 기존 역할 분리·자격 서명·암호화·이벤트 체인·검증 도구를 그대로 평가하고 새 프로토콜 조립을 피한다.
- 첫 신규 B-1 실험은 단일·다중·항목별 찬반으로 한정한다. Borda는 보류하며 기존 rank 기능은 변경하지 않는다. ‘연산 불가능’이 입증돼서가 아니라 검증 범위를 통제하기 위한 결정이다.
- Belenios의 기존 이벤트 체인을 확인했으므로 별도 중복 체인을 먼저 만들지 않는다. 원래 tracker·헤드와 모아이 확인증의 대응을 검토한다.
- 키 보관자에게는 모아이 서버와 독립된 고정 도구가 필요하다. 같은 최종 자료를 스스로 검증·집계하고, 그 한 대상에만 복호화 지분을 내도록 평가한다.
- 투표 복사·다른 자격으로 증명 재사용, 임의 부분합 복호화, 원래 재투표 정책과 모아이 정책의 차이를 새 필수 검토 항목으로 둔다.
- 후보 버전은 보안 변경·라이선스·실제 지원을 통과해야 한다. 현재 배포 목록과 소스 정보 확인은 채택 승인이나 안전성 검증이 아니다.

아래는 충족할 보안 요구와 논리 경계다. 기존 엔진의 암호문·직렬화·서명·집계 규격을 대체해 직접 구현할 명세로 사용하지 않는다. 실제 엔진과 충돌하면 그 차이를 먼저 보고하며 앞단 UX만으로 해결됐다고 표시하지 않는다.

## 1. 배경과 설계 기준

모아이투표는 문자 링크/코드로 참여하는 범용 투표 서비스다. 기존 구조는 본인확인과 평문 선택을 같은 서버가 처리하고, 마감 후 익명 투표 목록과 전체 해시를 공개한다. 서버가 기록과 해시를 함께 바꾸면 현재 서버 자료끼리의 비교로는 변경을 놓칠 수 있다.

사용자는 **투표 기록을 해시 체인으로 묶고, 참여자가 독립 보관한 확인증으로 서버 밖에 과거 기준점을 남기자**고 제안했다. 확인증은 분산원장의 역할 중 과거 기준값의 독립 보존을 일부 맡는다. 전체 원장 복제·채굴·화폐·합의 노드는 요구하지 않는다.

검토 과정에서 공개 평문 원장과 접수순 해시의 결합, 원시 DB 트랜잭션 메타데이터, 개인 확인과 전체 집계 증명의 차이가 확인됐다. 운영자를 신뢰하는 경량 경로 A는 기존의 ‘운영자도 개인 선택을 쉽게 연결하지 못해야 한다’는 요구를 충족하지 않는다.

**사용자가 그 요구를 낮추지 않았으므로 설계 기준은 경로 B-1이다.** 이는 사용자가 별도 운영 비용·제품 변경·실제 구현을 승인했다는 뜻이 아니다. 선거 생성 화면에 A/B 선택지를 추가하지 않으며, 요구가 다른 경로를 한 규격에 혼재시키지 않는다.

### B-1이 목표로 하는 것

- 올바른 클라이언트가 선택을 암호화하고, 서버·DB에는 평문 선택이나 이를 여는 비밀값을 보내지 않는다.
- 앱 운영자·DB 운영자 혼자서는 개별 표를 복호화하지 못한다.
- 체인에 들어간 확정 암호문 집합으로만 집계하고, 누구나 공개 자료로 집계와 결과 복호화 증명을 확인한다.
- 참여자는 자기 암호문과 당시 체인 기준점을 확인증으로 보관하고, 마감 후 포함·연결을 확인한다.

### B-1이 자동으로 보장하지 않는 것

- 같은 서버가 본인확인을 하면 신원과 암호문·참여 시각은 연결될 수 있다. 숨기려는 핵심은 그 암호문의 **선택 내용**이다.
- 운영자가 마음대로 바꿀 수 있는 웹 JS는 암호화 전에 선택을 빼돌릴 수 있다. B-1은 악성 배포에 대한 무조건 비밀성을 제공하지 않는다.
- 복호화 정족수 이상이 공모하거나 키가 유출되면 개별 암호문도 위험하다.
- 적격 등록·키 소유가 부정하면 암호화와 해시 체인이 유령 표를 막지 못한다.
- 소수 참여·만장일치·개인 선택의 자발적 공개 등 결과 자체의 추론은 남는다.

따라서 명칭은 ‘암호화 기표와 독립 집계 키 기반 공개 검증’으로 하며 **‘암호학적 완전 보호’**라고 부르지 않는다. 악성 클라이언트 배포까지 막는 B-2 수준이 필요하면 독립된 신뢰 클라이언트·배포 검증 등 추가 구조가 필요하다. 이 잔여 신뢰를 허용할지는 출시 전 확인해야 한다.

## 2. 범위와 현재 구현

현재 저장소의 [기표 API](../src/app/api/vote/link/route.ts)는 본인확인 토큰과 평문 선택을 받는다. [영수증 코드](../src/lib/verification.ts)는 선택·salt의 해시를 만들며, 공개 원장은 영수증 해시순 평문 목록이다. [현행 SQL](../supabase/migrations/20261010000000_ballot_types_and_secrecy.sql)의 rank는 STV/IRV가 아니라 `max_choices - r + 1` 보다식 점수 합계·1순위 수·순위별 수다.

이 구조는 B-1을 구현한 것이 아니다. 기존 로컬 파일 영수증 시제품과 테스트 96개·빌드 통과도 B-1의 보안 검증 결과가 아니다. 운영 DB의 스키마·로그를 이번 작업에서 조회하거나 실험하지 않았다.

B-1 신규 선거에서는 현행 `receipt_hash:selection` 개별 평문 목록 공개를 유지하지 않는 방향이다. 대신 암호문·유효성 증명·집계·결과 복호화 증명을 공개한다. 이는 제품 정책 변경이므로 구현 전 확인 대상이다. 기존 선거의 결과·기능을 삭제하거나 순위 투표를 비활성화하지 않는다.

분쟁용 개인정보 보관소·예외 복호화 키·관리자 비밀 복구는 범위에서 제외한다. **분쟁 키를 제외한 것과 집계 키 관리가 불필요한 것은 다르다.**

## 3. 구성요소

| 구성요소 | 역할 | 핵심 제한 |

| 시작 선언문 | 규칙·프로토콜·공개키·자격 기준·공개 기한 고정 | 최초 독립 사본과 비교. 현재 서버가 준 새 키 자동 신뢰 금지 |

| 자격 검사 | 적격 자격의 한 번 소비 | 운영자의 가짜 등록·발급까지 별도 검증 필요 |

| 집계 키 보관 주체 | 고정된 최종 합계만 부분 복호화 | 운영자 단독 정족수 금지. 개인 표·임의 부분집합 복호화 거부 |
| 공개 검증기 | 포함·연결·유효성·집계·복호화 증명 검사 | 검사한 항목별로 결과 표시 |

블라인드 서명은 B-1 선택 비밀성의 필수 전제로 고정하지 않는다. 공개키 암호문이 선택을 보호하는 것과 익명 자격증명이 신원-접수 연결을 줄이는 것은 서로 다른 목표다. 필요하면 별도 검토하되 이 기술만으로 시간/IP 추적·유령 발급이 해결된다고 하지 않는다.

## 4. 시작 선언문과 신뢰 앵커

선거 ID, 형식/암호 프로토콜 버전, 후보 ID·이름·순서, 선택/기권/순위 규칙, 자격 등록 기준과 고정값, 투표권 상한, 집계 공개키, 증명 검증키/매개변수, 체인 서명키, 최종 공개 기한·경로를 고정한다.

선언문에는 `trust_model: ENCRYPTED_TALLY_INDEPENDENT_KEYS_V1` 같은 검토용 식별자와 별도로 실제 보장·잔여 신뢰 목록을 넣는다. 식별자 문자열 자체가 보안 인증은 아니다.

전체 선언문 digest·전체 키 지문은 투표 전에 주최 측의 독립 사본 배포 경로로 확인할 수 있어야 한다. 짧은 지문은 표시용일 뿐 전체 앵커를 대체하지 않는다. 최초 독립 확인을 못 한 참여자는 `MANIFEST_ANCHOR_UNCONFIRMED`로 구분한다. 실제 문자 발송·외부 게시·저장소 공개 전환은 이번 작업에서 하지 않는다.

집계 키 보관자의 수와 정족수 k-of-m은 미정이다. 운영자 한 명 또는 같은 통제 주체가 정족수를 충족해서는 안 된다. 키 생성·보관·유실·교체·정족수 미달 시 결과 미공개 처리를 구체화해야 한다.

## 5. 기표 데이터와 유효성 증명

기록은 선언문·선거에 결합된 암호문 벡터와 그 유효성 증명으로 구성한다. 증명은 다른 선거·규칙·암호문에 재사용할 수 없어야 한다. 난수 재사용·작은 난수·잘못된 군 원소·키 바꿔치기·증명 누락을 거부한다. 실제 라이브러리·직렬화·군/보안 매개변수는 미선정이며 자체 암호 알고리즘을 만들지 않는다.

- 단일 선택: 허용 후보의 0/1 값과 정확한 선택 수/기권 규칙을 증명한다.
- 다중 선택: 후보별 0/1, 중복 불가, 최소~최대 선택 수와 기권 예외를 증명한다.
- 항목별 찬반: 각 항목의 유효한 찬반 표현과 전체 기권 규칙을 증명한다. 미응답을 임의로 반대로 계산하지 않는다.
- 보다식: 아래 별도 규칙을 만족하는지 검증해야 한다.

### 후속 검토용 보다식 인코딩 — 첫 실험에서 보류

후보×순위 행렬 M[a,r]를 암호화하고, 각 원소가 0/1임을 증명하는 접근을 검토한다. 행·열 합이 1 이하라는 조건만으로는 충분하지 않다. 예를 들어 1순위 없이 2순위만 채운 행렬도 그 조건을 통과하지만 현행 연속 순위 목록과 다르다.

필요 조건 후보:

```text
각 M[a,r] ∈ {0,1}
각 후보 행의 합 ≤ 1
각 순위 열의 합 q[r] ∈ {0,1}
q[r] ≥ q[r+1]                 # 빈 앞 순위 없이 연속
m = Σ q[r]
비기권이면 min_choices ≤ m ≤ max_choices
기권이면 허용된 경우에만 m = 0
점수[a] = Σ (max_choices-r+1) × M[a,r]
```

이 조건과 현행 canonical 인코딩이 정확히 같은 유효표 집합을 나타내는지 독립 검토해야 한다. 점수 합계·1순위 수·순위별 수는 행렬의 공개 합계에서 계산할 수 있다. 그러나 필요한 영지식 제약의 구현 지원·증명 크기·검증 성능은 확인되지 않았다.

순위 암호화 검증은 ‘불가능’으로 분류하지도, 행·열 조건만으로 ‘해결’했다고 하지도 않는다. 프로토콜 지원과 검토를 통과한 방식만 B-1 신규 선거에 제공한다는 원칙이며, 이번 문서가 기존 rank 기능 제거 결정은 아니다.

## 6. 자격과 유령 표 방지 — 별도의 출시 관문

N 상한·명부 루트·nullifier·해시 체인은 운영자가 미투표자 몫으로 만든 정당해 보이는 표를 자동 차단하지 못한다. 다음을 확정해야 한다.

1. 적격 사람과 등록 키/자격을 누가 어떤 근거로 연결하는가?
2. 운영자가 모르는 비밀을 유권자가 실제로 보유하는가?
3. 미등록·미참여자의 키를 운영자가 대신 등록·발급할 수 없게 누가 검증하는가?
4. 공개 검증기가 자격의 유효한 한 번 사용을 어떻게 검증하며 신원은 어떻게 보호하는가?
5. 기기·자격 분실과 새 자격 발급이 중복 사용 우회가 되지 않는가?

유권자 기기 공개키나 Passkey도 그 최초 등록을 운영자가 조작할 수 있으면 충분하지 않다. 로그인 증거를 그대로 기표 서명으로 취급하지 말고 선거·암호문·요청 내용을 명시적으로 결합해야 한다. 암호화 집계만 구현한 단계는 `ELIGIBILITY_UNPROVEN` 상태이며 ‘운영자 유령 표 방지’라고 표시하지 않는다.

본인에게 투표권 사용 여부만 알려주는 조회는 후보지만, 악성 서버의 거짓 응답을 독립적으로 반박하는 증거가 자동으로 생기지는 않는다. 조회 결과에는 개인 암호문 위치나 선택을 연결하지 않는다. 강제 유료 통지를 채택하지 않는다.

### 6.1 생성자 선택: 기표 직전 휴대폰 문자 인증 필수

사용자 요청으로 **선거 생성자가 ‘기표 직전 휴대폰 문자 인증 필수’를 선택할 수 있게 한다.** 기본값은 해제다. 해제해도 해당 선거의 기본 로그인·투표 자격 검사는 유지한다. 이 절은 신규 설계이며 현재 제품에 구현된 옵션이 아니다.

생성 화면 문구:

> 기표 직전 휴대폰 문자 인증 필수  □
>
> 투표를 제출하기 전에 명부에 등록된 휴대폰으로 인증합니다. 중요한 투표에서 추가 확인에 사용할 수 있습니다. 문자 발송 비용이 발생하며, 휴대폰을 사용할 수 없으면 투표를 제출할 수 없습니다.

선거 시작 전에 정하고 시작 선언문에 고정한다. 검토용 정책값은 `precast_auth: standard | sms_otp_required`로 구분한다. 이는 Belenios의 실제 지원 필드가 아니라 모아이 연동 요구다. 선거가 열린 뒤 관리자가 인증을 끄거나 전화번호를 바꿔 우회하지 못하게 한다. 번호 정정·휴대폰 미보유자의 처리 정책은 개표 비밀성·자격 정책과 함께 시작 전에 정하며, 기표 화면에서 임의 번호로 인증 대상을 바꾸지 않는다.

제출 흐름:

1. 유권자가 선택을 확인하고 클라이언트가 암호화된 기표문을 준비한다.
2. 필수 선거이면 마지막 제출 단계에서 등록 휴대폰의 마스킹된 번호를 보여주고 새 인증번호를 요청한다. 과거 로그인·초대 문자 수신만으로 이 단계를 통과하지 않는다.
3. 인증 성공 후 짧은 유효기간의 1회 제출 승인을 발급한다. 승인은 선거·인증 주체·세션 및 정확한 제출 기표문의 digest에 결합한다. 선택 평문을 인증 서버에 보내지 않는다.
4. 실제 기표 접수 경계는 **독립 투표 자격의 유효한 서명과 문자 인증 승인 모두**를 검사한다. 엔진 직접 호출·다른 API·관리자 경로로 인증을 건너뛰지 못해야 한다. Belenios Connect 등 외부 인증의 실제 규격과 확정 시점이 이를 지원하는지 PoC에서 확인한다.
5. 인증 승인의 소비와 기표 확정을 안전하게 연동한다. 같은 기표문이 이미 확정된 뒤 응답만 유실되면 기존 공개 기록·확인증을 돌려주며 새 문자나 새 표를 요구하지 않는다. 다른 기표문·다른 선거에 승인을 재사용하는 것은 거부한다. 인증 완료가 투표 마감을 연장하지는 않는다.

인증번호는 암호학적 난수로 생성하고 짧게 만료시키며 한 번만 사용한다. 재발송 시 이전 번호를 무효화하고 실패 횟수를 초기화하지 않는다. 번호·선거·계정·접속 경로별 발송/검증 제한과 발송 중복 방지를 둔다. 정확한 자리 수·유효기간·허용 횟수·비용 한도는 구현 전 고정한다. 발송 장애·번호 누락·인증 실패 때 필수 조건을 자동 해제하지 않는다. 인증번호·비밀 자격·요청 본문을 로그/오류 추적에 남기지 않는다.

**문자에는 인증번호와 최소한의 선거 안내만 넣는다.** 독립 발급자가 만든 비밀 투표 자격은 모아이·공용 문자 게이트웨이를 경유하지 않는 별도 경로로 전달한다. 별도 도메인이나 프로세스를 두어도 같은 운영자가 비밀값에 접근할 수 있으면 실질적 역할 분리가 아니다.

이 옵션은 등록 휴대폰을 현재 사용할 수 있는지 추가로 확인한다. 실명·투표 의도·독립 자격의 정당성을 단독으로 증명하지 않으며 운영자가 통제하는 OTP 발급만으로 유령 표 방지가 완성되지 않는다. SIM 탈취·번호 이전·문자 가로채기·피싱 위험도 남는다. 인증 서버가 신원과 암호문을 연결할 수 있다는 B-1의 잔여 신뢰는 유지하며 공개 원장에는 전화번호·인증 정보가 들어가지 않는다.

인증번호의 1회 사용·시도 제한과 PSTN 위험에 대해서는 [NIST SP 800-63B-4의 대역 외 인증 지침](https://pages.nist.gov/800-63-4/sp800-63b.html)을 기술 참고로 삼는다. 이를 모아이의 법적 의무나 구현 완료의 근거로 표시하지 않는다. 이번 단계에서는 모의 발송으로만 시험을 설계하며 실제 유료 발송은 하지 않는다.

## 7. 체인과 발급 즉시 확인증 검증

확정 record에는 암호문·유효성 증명·선언문 결합을 포함한다. 실제 바이트를 정규 직렬화한 digest를 체인에 기록한다. 민감한 신원·토큰·IP는 공개 이벤트에 넣지 않는다.

```text
record_digest = SHA256(C(domain, manifest_hash, encrypted_record))
H0 = SHA256(C(genesis_domain, manifest_hash))
Ei = {version, election_id, manifest_hash, index, kind, payload}
Hi = SHA256(C(chain_domain, H(i-1), Ei))
```

이것은 논리적 식이다. 실제 정규 직렬화·숫자·바이트·도메인 규격은 별도 확정한다. 매번 과거 전체를 복사하지 않아도 직전 해시가 과거를 결합한다. CRC·수정 시각 섞기·사전 N개 빈 영수증은 사용하지 않는다.

확인증에는 자기 record_digest, E_i, previous_hash, index, H_i, 선언문/키 식별자와 서버 서명을 넣는다. 브라우저는 자기가 만든 암호문과 digest를 대조하고 H_i·서명을 즉시 검증한다. 이것은 기록 포함 확인이며 선택 의도 확인과 다르다.

개인 파일에 암호화 난수 등 표를 열 수 있는 값을 보관할지는 선택·강요 위험을 포함해 별도 결정한다. 공개 조회는 그런 비밀을 반환하지 않는다. 공개 record ID·digest·c는 소유 증명이 아니다. 약 12자리 표시는 파일 식별용이며 원본을 복구하는 키가 아니다.

## 8. 원자성·마감·재조회

선거별 헤드 잠금, DB 기준 마감 검사, 자격 소비·암호문 기록·이벤트·헤드의 원자적 확정, 동일 경계의 final 처리를 상세화한다. 암호문을 저장하므로 신원-암호문이 xmin/WAL로 연결될 수 있어도 그것만으로 평문 선택이 드러나지 않아야 한다. 이는 시각·신원 자체의 익명화와 다르다.

**명부 소비를 먼저 커밋하고 평문 선택을 인메모리 큐에 넘기는 안은 채택하지 않는다.** 장애 시 자격만 사라질 수 있고 지연·배치만으로 원시 메타데이터 추적이 제거되지 않는다. 암호문 저장과 확정 상태 기계를 우선한다.

서명과 DB 커밋의 경계를 정한다. 커밋 전 서명 실패는 롤백할 수 있으나 발급된 완료 서명을 커밋 전 외부에 내보내지 않는다. 외부 키 서비스라면 `COMMITTED_SIGNING_PENDING` 등 상태와 재시도를 정의한다. 네트워크 원자성을 DB 트랜잭션이 해결한다고 가정하지 않는다.

재조회 규칙:

- 공개 record ID로 원장에 있는 이벤트·서명만 받는 것은 익명 공개 조회다.
- 소비된 토큰+존재하는 공개 record ID를 보고 두 값이 같은 투표에 속한다고 주장하지 않는다.
- 클라이언트는 자기가 만든 동일 암호문·기록 식별값으로 공개 접수 상태를 확인한다. 신원과 개인 기록의 대응을 복구하는 기능은 만들지 않는다.
- 전원 불변식은 기록·vote 이벤트·허용된 자격 소비가 일치한다는 것이다. 특정 소비 토큰과 공개 기록의 관계를 저장하지 않는다면 모든 소비 토큰+임의 기록 조합이 개인별로 대응한다고 검사할 수는 없다.
- 동일 기록 재요청, 다른 내용의 식별값 충돌, 미접수, 이미 다른 기기로 소비된 상태를 구분한다.

개인 비밀값 분실 복구와 공개 증명 재다운로드는 별개다. 전자는 제외한다.

## 9. 마감 집계와 독립 키 통제

1. 고정된 마감 경계에서 유효·확정 vote 이벤트와 암호문 집합을 결정한다.
2. 최종 이벤트는 선언문·체인 헤드·암호문 목록·증명·유효표 수·집계 명세의 digest를 고정한다.
3. 누구나 **그 정확한 암호문 집합**을 동형 집계한다. 임의 누락·추가·부분집합을 거부한다.
4. 독립 키 보관 주체들이 최종 집계 암호문만 부분 복호화하고 올바름의 증명을 제공한다.
5. 검증기가 집계 재계산과 복호화 증명을 검사해 공개 결과를 확인한다.

체인에 포함된 암호문이 실제 입력인지를 검사해야 체인-집계 분리가 막힌다. 암호문이 있다는 사실만으로 자동 해결되지 않는다. 키 보관자는 개별 표·임의 작은 부분집합·서로 다른 집계본의 복호화 요청을 거부해야 한다. 여러 부분집합의 차이로 개인 표를 알아내는 공격도 시험한다.

키 보관자가 정족수 이상 공모하면 이 제한은 깨질 수 있다. 정족수 미달·키 유실·복호화 증명 실패 때 결과를 추정하거나 서버가 대체키로 복구하지 않는다. 수동 키 의식·마감 시 독립 보관자 참여가 필요할 수 있으므로 ‘완전 무인 운영’은 보장하지 않는다. 상시 자동 키 서비스를 택하면 독립 통제와 임의 복호화 방지 정책을 새로 검토한다.

## 10. 원장 공개·앵커·검증 상태

공개 묶음은 선언문, 서명된 최종 기준점, 암호문·유효성 증명, 이벤트, 정확한 집계 입력 목록, 결과 및 부분 복호화 증명으로 구성한다. 개인 평문 표 목록은 공개하지 않는다.

최초 선언문과 최종 digest를 운영자가 단독으로 바꾸지 못하는 통제 주체의 사본에 보존하고 서로 비교한다. 별도 감시자 앱을 먼저 만들지는 않는다. 두 URL·도메인·Git Release가 같은 운영자 통제라면 독립성으로 계산하지 않는다. Git/스토리지의 삭제·교체 가능성과 보존 정책도 명시한다.

검증 보고서는 하나의 VALID 값 대신 항목을 분리한다.

| 상태 | 의미 |
|---|---|
| RECORD_INCLUDED | 자기 암호문 기록이 원장에 포함 |
| HISTORY_LINK_VERIFIED | 저장 기준점과 최종 체인이 연결 |
| BALLOT_RULES_VERIFIED | 제출 암호문의 규칙 증명 검사 통과 |
| TALLY_VERIFIED | 고정 입력 집계와 결과 복호화 증명 일치 |
| ELIGIBILITY_UNPROVEN | 실제 적격 자격 검증 미완료 |
| CAST_AS_INTENDED_UNVERIFIED | 암호문이 사용자의 의도와 같은지 독립 검사 미완료 |
| MANIFEST_ANCHOR_UNCONFIRMED | 최초 선언문의 독립 확인 없음 |
| PROOF_UNAVAILABLE / PUBLICATION_OVERDUE | 필요한 자료 부족 / 공표 기한 경과 |
| SIGNED_HISTORY_CONFLICT | 유효한 동일 앵커의 서명 자료가 실제로 양립 불가 |

키 오류·서명 위조·형식 오류·손상 파일을 상충하는 유효 서명과 구분한다. 검증 불가도 눈에 띄는 미완료 상태로 표시하되 조작 확정으로 자동 판단하지 않는다. 분쟁용 기술 리포트에는 비밀값·개인 정보 없이 필요한 공개 증거만 넣는다.

## 11. 사용자 경험과 남는 위험

사용자는 ‘확인증 저장’과 ‘내 기록·집계 확인’만 기본으로 이용한다. 이 화면은 선택 내용 확인과 기록 포함 확인을 혼동하지 않아야 한다. 암호문만 확인했는데 ‘내가 의도한 후보에게 정확히 투표됨’이라고 표시하지 않는다.

Benaloh/검증용 기표 같은 의도 확인 장치를 검토할 수 있지만, 이것도 악성 JS의 평문 유출 자체를 막는 장치가 아니다. 검증 도구와 기표 클라이언트의 신뢰 문제를 구분한다. 의도 검사를 1차에서 연기한다면 E2E 검증 완성을 주장하지 않는다.

소수 참여·만장일치·다수 공모 시 합계로 개인 선택을 유추할 수 있다. 공개 하한·경고 정책은 별도 확정한다. 기존 salt 기반 영수증의 강요·양도 문제를 그대로 새 모드의 보장으로 가져오지 말고, 선택한 암호 프로토콜의 영수증 자료가 만드는 위험을 새로 검토한다.

## 12. 구현 전 검증 관문

- 실제 유지되는 프로토콜/라이브러리 선정과 독립 암호 검토. ElectionGuard류는 후보 참고이며 지원 방식·유지 상태를 확인하기 전 채택하지 않는다.
- 적격 등록·자격 증명의 신뢰 주체 확정. 유령 표 삽입과 가짜 등록을 시험한다.
- 후보별 0/1·선택 수·기권·보다식 연속 순위 제약의 악성 입력 시험.
- 체인은 두고 집계만 변경, 암호문 누락/중복, 잘못된 복호화 증명, 분기·키 교체 시험.
- 원시 DB의 xmin·ctid·WAL·백업을 제공한 공격자에게 암호화 난수·평문·집계 키가 없는지 검사. 트랜잭션 분리만으로 무연결을 주장하지 않는다.
- 응답 유실·동시 접수/마감·서명 대기·키 보관자 장애를 주입한다.
- 실제 규격과 단말로 자료 크기·메모리·시간·처리량을 측정한다. 1초·3초·5천 건 같은 미측정 수치를 설계 보장으로 쓰지 않는다. 필요할 때 머클·배치를 추가한다.
- 서버와 독립 검증기의 동일 벡터 결과를 비교한다. 단위 테스트로 암호 프로토콜의 보안을 증명했다고 하지 않는다.

이 관문과 운영 주체·잔여 신뢰 확인 전에는 구현 착수 가능 또는 출시 가능으로 승인하지 않는다. 기존 앱·기존 선거는 자동 전환하지 않고 공유 인증·다른 앱 DB를 변경하지 않는다.
