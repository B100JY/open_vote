# 원장 확인증 설계 — 두 외부 검토의 통합 판정

> **최신 확정 계획:** [v1.0 기존 서비스 기반 경량 감사 계획](voting-native-audit-plan-2026-10-28.md)이 우선한다. Belenios 도입과 운영자 비신뢰 B-1 연구는 보류하고, 기존 모아이에 표준 해시·서명·숨김 약정·공개 집계 재검증을 추가한다. 아래는 과거 검토 기록이며 현재 구현 완료를 뜻하지 않는다.

- 작성: 2026-10-28
- 대상: [설계안](ledger-witness-design-2026-10-28.md), [재검토 의뢰서](ledger-witness-review-request-2026-10-28.md)
- 출처: 사용자가 대화에 전달한 두 검토문. 첫 문서는 번호 1~7, 두 번째는 F1~F12로 구분한다.
- 작성자가 확인한 범위: 저장소의 관련 코드·SQL과 아래 일차 자료. 운영 DB·로그·실제 부하·암호 구현은 검증하지 않았다.
- 상태: 설계 검토 결과의 수용·정정 기록. 코드·DB·배포 변경 없음. 외부 검토문 원문을 고쳐 쓴 보고서가 아니다.

**현재 판정은 §6(v0.6)과 추가 §7(v0.7)을 우선한다.** B-1 요구와 기존 엔진 우선 평가를 유지하며, 생성자 선택형 기표 직전 문자 인증을 설계에 추가했다. 실험을 실행했거나 통과한 것은 아니다.

**v0.5 후속 상태:** 아래 §1~§3은 v0.4 당시의 두 경로 비교다. 이후 두 재검토까지 반영한 현재 설계는 기존 요구를 유지하는 **B-1(암호화 기표·독립 집계 키)**을 기준으로 한다. 운영자 신뢰로 요구를 낮춘다는 답변은 없었으므로 A를 기본으로 선택하지 않았다. 이는 운영자에게도 무조건 안전하다는 승인이나 실제 키 운영 비용·구현 승인을 뜻하지 않는다. 새 판정은 §5를 우선한다.

## 1. 먼저 결정해야 할 신뢰 모델

첫 검토는 운영자까지 보호하는 암호화 기표·익명 자격 검증을 요구한다. 두 번째 검토는 운영자가 실시간 선택을 볼 수 있다는 신뢰 가정을 공개하는 제한적 1차 버전을 권고한다. **같은 요구를 만족하는 대안 두 개가 아니라, 서로 다른 보장 수준이다.**

기존 사용자 요구는 관리자·운영자가 쉽게 신원과 선택을 연결하지 못하는 방향이다. 두 번째 검토문을 전달했다는 사실만으로 이 요구를 낮추는 데 동의한 것으로 취급하지 않는다. 사용자에게 신뢰 모델 선택을 요청했으며, 확정 전에는 기존 요구를 유지한다.

| 경로 | 보장 목표 | 현재 판단 |
|---|---|---|
| A. 운영자를 신뢰하는 제한적 감사 | 공개 자료의 순서 연결을 막고, 본인이 자기 표를 검증하며, 공개 평문 결과를 재계산 | 조건부 후보. 운영자·원시 DB 관리자에 대한 비밀성까지 주장할 수 없음. 명시적 요구 조정 필요 |
| B. 운영자에 대해서도 선택 보호 | 암호화 기표·독립 키 통제·자격/기표 분리 등으로 연결을 어렵게 함 | 기존 목표에 대응. 프로토콜과 남는 신뢰 가정의 재설계·독립 검토 필요 |

분쟁 증빙용 키 체계를 제외한 것은 투표 집계용 독립 키 관리까지 금지한다는 뜻이 아니다. B에 필요하다면 집계 키 구조를 별도로 검토한다. 단, 정족수 이상 공모·악성 클라이언트 배포까지 자동 해결된다고 하지 않는다.

## 2. 항목별 수용과 정정

### R1. 순서와 평문 digest의 대응 — 수용

접수순 이벤트의 결정적 digest를 최종 평문 행에 대입해 연결할 수 있다는 지적은 타당하다. 이것은 출시를 막는 문제다. 다만 외부 관찰만으로 언제나 모든 표가 100% 특정된다는 주장은 관찰 범위·동시성·보조 정보에 달린 조건부 주장이다. 운영자가 신원과 평문을 같은 요청으로 받으면 직접 연결할 수 있다는 점은 별개로 분명하다.

F1의 숨김 약정 후보:

```text
k = 브라우저의 독립적인 32바이트 난수
c = SHA256(C({ domain: "moai-commit-v1", election_id, manifest_hash, receipt_hash, k }))
```

k를 공개하지 않고 안전하게 생성한다는 조건에서 공개 자료의 단순 대입 연결을 막는 후보로 검토한다. receipt_hash는 선택과 salt에 결합되어야 한다. 다만 기표 서버가 c와 receipt_hash를 동시에 받는다는 사실은 사라지지 않는다. 이를 운영자 익명화 또는 원시 DB 조회 익명화로 확대하지 않는다.

### R2. 원시 DB 메타데이터 연결 — 추가 필수 보완

두 검토의 최소 보완만으로는 놓칠 수 있는 경로다. PostgreSQL의 `xmin`은 해당 행 버전을 삽입한 트랜잭션의 식별자이며, UPDATE도 새 행 버전을 만든다. 명부 소비와 평문 투표지 INSERT를 같은 트랜잭션에서 처리하면, 일상 필드에 시각·명부 ID를 넣지 않아도 원시 SQL 읽기 권한자가 같은 트랜잭션 식별자로 대응을 좁히거나 연결할 수 있다.

따라서 **‘운영자는 제외하되 DB 조회 관리자는 보호’라는 표현도 관리자 권한 범위를 정하지 않으면 성립하지 않는다.** 제한된 앱 API/집계 뷰만 보는 역할과 시스템 칼럼·WAL·백업에 접근하는 DB 관리자는 다르다. 이 위험 때문에 원자성을 제거하자는 뜻은 아니다. 원자성은 보존하면서 공개·보관할 데이터를 암호화하거나 신원 경계를 분리할 방법을 검토해야 한다.

이것은 공식 DB 동작과 저장소 SQL로부터 도출한 공격 가설이다. 운영 DB에서 실제 연결을 시도하지 않았다. 운영 데이터 대신 격리 DB에서 raw row version·트랜잭션 경계를 포함한 공격 시험이 필요하다.

### R3. 유령 표·자격 검증 — 문제 수용, 처방은 조건부

N 상한·서명·해시 체인으로 미참여자 몫의 가짜 표를 막지 못한다는 지적은 수용한다. 다만 다음 장치의 보장 범위를 구분한다.

- 명부 머클 루트는 특정 목록의 고정/포함을 증명할 뿐 목록의 사람과 키가 진짜 유권자의 것인지 보장하지 않는다.
- nullifier는 적절한 비밀 소유·멤버십 증명·선거 범위 결합이 있을 때 중복 사용을 검출한다. 운영자가 만든 가짜 키를 명부에 넣으면 중복 없는 가짜 표도 가능하다.
- 블라인드 서명 발급자가 키를 지배하면 미발급자 몫을 임의로 발급할 수 있는 문제를 별도로 다뤄야 한다.
- 본인 투표권 사용 여부 조회는 선택 조회와 다르므로 후보로 채택할 수 있다. 그러나 사용자가 확인해야 탐지할 수 있고, 같은 악성 서버가 상태를 거짓 응답하는 경우도 있다.
- 소비 수·이벤트 수·유효표 수의 일치는 필요한 일관성 검사지만 합법적인 참여자의 실제 의사까지 증명하지 않는다.

필수 결정은 ‘누가 적격 키/자격을 등록하고, 운영자가 모르는 비밀을 누가 소유하며, 위조 발급을 누가 검증하는가’다. 전체 이름·연락처나 단순 식별자 해시를 명부 증명이라고 공개하지 않는다. 강제 문자 통지는 보장 대안으로 확정하지 않으며 실제 발송도 하지 않는다.

### R4. 숨김 약정과 전체 집계 연결 — 수용

숨김 약정을 열지 않으면 공개 순서와 평문 선택의 대응을 끊을 수 있는 대신, 누구나 약정 집합과 평문 집합의 일치를 검사하기 어렵다는 F5 지적은 수용한다.

경로 A의 문구는 ‘각자가 자기 표의 결합을 확인하고, 누구나 공개 평문 목록의 표 수·집계를 재계산한다’로 제한해야 한다. 체인만 그대로 두고 확인하지 않는 사람의 평문 한 행을 바꾸는 공격은 당사자 확인 또는 별도 증명 없이는 놓칠 수 있다.

단, 이 관계의 보편 검증이 모든 암호 체계에서 불가능하다는 일반 명제로 확대하지 않는다. 영지식 관계 증명·검증 가능한 변환 등은 별도 접근이다. 적용 규격 없이 두 digest를 함께 서명하는 것은 증명을 대신하지 못한다.

### R5. 발급 즉시 포함 확인 — 수용

단일 vote 이벤트의 기준점이라면 확인증에 previous_hash, 정확한 이벤트 E_i, index, H_i, 선거 선언문과 키 식별자, 서버 서명을 담는다. 클라이언트는 자기가 만든 c와 이벤트를 비교하고 H_i를 재계산한 뒤 서명을 확인한다.

이는 서버가 서명한 그 이벤트가 기준점에 결합됐다는 확인이다. 해당 기록이 정당한 투표권으로 접수됐거나 모두에게 같은 분기를 줬다는 보장은 아니다. 배치를 쓸 때는 같은 정보를 단순 복사하지 말고 배치 포함 증명과 배치 기준점을 검증해야 한다.

### R6. 분기·서명의 증거 범위 — 부분 정정 후 수용

시작 선언문·전체 공개키 지문과 최종 서명 digest를 서버 밖에 사전/사후 보존하는 방안은 수용한다. 공개 Git 커밋·Release도 관리자에 의해 삭제·교체될 수 있으므로 ‘변경 불가능’한 장소로 자동 분류하지 않는다. 서로 다른 통제 주체의 사본과 기록 보존 정책이 중요하다. 두 URL이 같은 운영자 통제라면 독립성도 제한된다.

첫 검토의 ‘제3의 증거가 없으면 로컬 위조인지 판정 불가’는 서버 서명이 유효하고 키가 사전 고정됐다는 조건에서 과도하다. 사용자는 개인키 없이 서버 서명을 만들어 낼 수 없으므로 유효 서명 확인증은 발급 주체에 대한 기술적 근거다. 다만 법률상 증거력과 부정행위 확정은 별도다.

연결 자료를 받지 못한 경우와 완전한 유효 서명 자료 둘이 실제로 양립 불가능한 경우를 구분한다. 전자는 `PROOF_UNAVAILABLE`, 후자는 자료를 갖춰 `SIGNED_HISTORY_CONFLICT`로 표시한다. 키·선언문이 다르거나 파일이 손상된 오류도 따로 분리한다. ‘연결 증명 없음 → 선거 전체 조작 확정’ 자동 규칙은 채택하지 않는다.

검증 불가는 조용한 성공 상태로 처리하지 않는다. 공개 기한과 필요한 파일을 선언문에 넣고 기한 경과 시 눈에 띄는 미검증 상태로 표시한다. 평가는 엄중하게 하되 원인 판단을 위조하지 않는다.

### R7. 탐지 확률식 — 제한적으로만 참고

`(1-p)^k`는 k개 개별 표를 각각 독립 확률 p로 검사하는 등의 가정에서 참고할 수 있다. 체인 앞부분 수정이 뒤의 여러 확인증과 충돌하거나, 운영자가 비검증자를 선별하거나, split view를 쓰는 경우에는 그대로 적용할 수 없다. 제품의 보안 확률로 표시하지 않는다.

### R8. 실제 순위 방식과 집계 — 정정 후 수용

저장소의 현재 rank 집계는 `max_choices - r + 1` 점수 합계, 1순위 수, 순위별 수를 계산하는 **보다식 점수 방식**이다. STV/IRV의 탈락·표 이전 구현으로 확인되지 않았다. 근거는 `20261010000000_ballot_types_and_secrecy.sql`의 rank 분기와 결과 UI다. 운영 DB의 동일성은 이번에 확인하지 않았다.

따라서 STV의 비선형성을 이유로 현재 rank 기능을 즉시 제거한다는 권고는 그대로 적용하지 않는다. 암호화 방식의 지원 여부도 별도 검토한다. 순위 점수 합계는 선형 성분으로 표현될 여지가 있지만 순위 중복·범위·부분 순위 유효성 증명까지 자동으로 해결되는 것은 아니다.

동형 집계는 각 개인 표를 평문 복호화하지 않고 합산할 수 있지만, 평문 최종 합계를 얻는 복호화와 그 올바름의 증명은 필요하다. 다중 선택·찬반도 프로토콜에 따라 가능하므로 ‘단일 찬반만 가능’이라고 고정하지 않는다. 기존 기능의 삭제·비활성화는 이번 문서 작업에서 하지 않는다.

### R9. 원자성·재시도 — 수용하되 공개 c 인증 주장은 거부

선거별 헤드 잠금, DB 시각으로 마감 판정, 투표권 소비·기록·이벤트·헤드의 원자적 확정, 같은 잠금 아래의 final 처리는 상세 설계 후보로 수용한다. 서명 위치에 따라 롤백 가능 경계·확정 후 서명 대기를 구분한다. 외부 키 서비스를 쓰면 별도 장애 상태가 필요하다.

F7의 **‘c는 추측할 수 없으니 c를 아는 것이 소유 증명’은 공개 후에는 성립하지 않는다.** c가 공개 체인에 있으면 누구나 읽는다. 소비된 임의 토큰과 공개 c가 함께 왔다는 이유로 둘이 같은 투표였다고 판단해서도 안 된다.

재조회는 두 경우로 나눠 설계한다.

1. 공개 이벤트·서명만 반환: 익명 공개 조회로 취급할 수 있다. 개인 소유나 해당 토큰과의 대응을 주장하지 않는다. 클라이언트가 보관한 k/salt/선택과 비교해 자기 기록인지 확인한다.
2. 비공개 상세·원본 비밀값·상태 전환 포함: c 외 별도의 비밀 소유 증명 또는 자격 프로토콜이 필요하다. 원본 비밀값은 클라이언트에만 남기는 기본안과 충돌하지 않는지 검토한다.

이미 발급된 공개 증명을 다시 받는 접수 확인과, 분실한 개인 영수증 비밀값을 복구하는 기능은 다르다. 전자는 검토하고 후자는 기본안에서 계속 제외한다. 명부 행에 멱등 키를 붙이는 방식과 원시 트랜잭션 상관관계는 R2와 함께 검토한다.

### R10. 배치·머클·성능 — 측정 후 결정

두 검토의 ‘대규모에서 병목이 심함’과 ‘10만 이벤트는 모바일 1초’는 형식·단말·구현·서명 빈도·입력 크기·WebCrypto 호출 방식·동시성 측정 없이 확정할 수 없다. 수치는 검증 결과로 인용하지 않는다.

우선 선형 체인의 최소 구현을 격리 환경에서 측정하고, 표준 기기/입력 규모·메모리·다운로드·시간·마감 직전 부하로 필요성을 결정한다. 마이크로 배치는 처리량 후보이지 익명화·검증 가능한 셔플의 대체가 아니다. 포함 증명은 부분 포함만 보이며 집계·자격·과거 일관성까지 자동 증명하지 않는다.

### R11. 공통적으로 바로 반영할 결정

- 최초 선언문·전체 공개키/키 지문을 독립 사본에 고정하고 검증기는 현재 서버의 새 키를 자동 신뢰하지 않는다.
- 단축 지문은 사람용 표시일 뿐 전체 신뢰 앵커를 대신하지 않는다. 투표 전에 앵커를 받지 못한 사람의 한계도 표시한다.
- 선거별 정규 인코딩·무효/기권·집계·동률 처리와 공개 기한을 고정한다. 규정에 없는 승자 결정 규칙을 새로 만들지 않는다.
- 강요·영수증 양도, 결과 자체의 소수 참여·만장일치 노출은 잔여 위험이다. 공개 제한/경고 정책은 별도 결정이며 임의로 비활성화하지 않는다.
- 강제 문자 발송·외부 게시·저장소 공개 전환은 이 검토에서 실행하지 않는다.

## 3. 다음 단계와 출시 조건

먼저 A/B 신뢰 모델을 확정한다. 이후 그 목표에 맞는 공개 형식·자격 발급·개인 포함·체인과 집계 결합을 하나의 규격으로 검토한다. 단순한 경로 A를 선택하더라도 ‘전체 기록의 정당성을 누구나 증명’ 또는 ‘DB 관리자에게 비밀’이라고 확대하지 않는다.

출시 전에는 R1/R2/R3/R4/R9를 포함한 공격 시험과 별도 검증기의 교차 검사를 통과해야 한다. 문서 변경이나 단위 테스트만으로 항목을 ‘해결’로 표시하지 않는다. 이번 작업은 두 검토를 수용·정정한 것이며 구현 검증은 아직이다.

## 5. v0.4 재검토 두 건의 추가 판정 — v0.5 반영

출처는 사용자가 후속 대화로 전달한 1~8번 검토와 G1~G8 검토다. 두 검토의 합의는 ‘기존 요구를 유지하면 A는 부족하다’는 것이다. 사용자 요구를 낮추지 않고 B-1을 현 설계 기준으로 삼았다. A를 선거 생성 시 선택 가능하게 출시하는 결정은 하지 않았다.

### S1. B와 ‘완전 보호’의 구분

서버·DB에 암호문만 보관하고 키 정족수를 운영자 밖에 두면, xmin 등으로 신원과 암호문이 연결돼도 선택 평문은 별도로 보호할 수 있다. 신원·시각 자체가 숨겨진다는 뜻은 아니다. 악성 웹 JS가 암호화 전 선택을 유출하는 위험은 남는다. 기표 의도 검사는 잘못 암호화한 선택을 검사하는 장치이지, 그 평문을 다른 곳으로 전송하지 않았다는 증명이 아니다. 따라서 B-1을 ‘완전 보호’로 부르지 않는다.

### S2. 물리 메타데이터와 큐

xmin뿐 아니라 WAL·행 버전·물리 위치·백업·로그를 고려한다는 G2 지적을 수용한다. 다만 xid는 장기적으로 wraparound가 있고, ctid는 갱신·이동에 따라 변하므로 항상 단조·정확한 개인별 순서표라고 가정하지 않는다. 위험의 존재와 언제나 100% 연결이라는 주장을 구분한다.

명부 소비를 먼저 커밋한 뒤 평문 선택을 인메모리 큐로 넘기는 처방은 채택하지 않는다. 장애 시 자격만 소비될 수 있고, 큐·지연·배치의 트래픽 상관관계도 남는다. 암호문 저장과 원자성·확정 상태 기계를 우선한다. ‘상관계수 약 1/N’ 시험 하나로 익명성이 입증됐다고 하지 않는다.

### S3. 공개 재조회

공개 이벤트와 서버 서명만 반환하는 익명 조회는 개인 비밀 복구와 분리한다. 공개 record ID가 소유 증명이라는 주장은 계속 거부한다. 소비 토큰+존재하는 c를 처리하더라도 해당 토큰과 c가 연결됐다고 반환하거나 저장하지 않는다. 원자성이 모든 소비와 기록의 개수 일치를 보장할 수 있어도, 저장하지 않은 모든 개인별 대응까지 증명한다는 뜻은 아니다.

API가 어떤 평문 선택도 반환하지 않아야 한다는 정적 검사를 기존 앱 전체에 무조건 적용할 수는 없다. 현행 A형 공개 결과에는 평문 목록이 있다. 신규 B-1 모드의 개인 선택·비밀 반환 금지와, 기존 공개 원장의 의도된 평문 공개를 구분한다. 이번에는 실제 API를 바꾸지 않았다.

### S4. 자격·키 등록

기기 생성 공개키나 Passkey를 사용해도 최초 등록을 운영자가 바꿀 수 있으면 미참여자 몫의 가짜 키를 넣을 수 있다. 인증 성공을 곧바로 사용자의 해당 암호문 기표 의사로 간주하지 않는다. 자격 등록 주체·유권자 비밀 소유·위조 발급 방지·공개 자격 증명을 별도 출시 관문으로 유지한다.

### S5. 보다식 증명

보다식은 선형 합계를 구성할 수 있으나, G4의 행·열 합 1 이하만으로 현행 유효표가 되지는 않는다. ‘1순위 없음·2순위만 있음’도 그 제약을 통과한다. v0.5는 q[r]≥q[r+1] 연속성, min/max 선택 수, 기권 조건, 모든 원소 0/1을 추가했다. 이는 검토해야 할 수학적 명세이며 해당 라이브러리가 지원한다는 확인은 아니다. 신규 암호 모드 지원 보류와 기존 rank 기능 삭제는 다르다.

### S6. ‘암호문 체인 = 집계 입력’의 검사

G3의 방향을 수용하되 등호를 구성만으로 가정하지 않는다. 검증기가 확정된 유효 vote 이벤트의 정확한 암호문 목록을 구성하고, 누락·중복·교체·추가를 거부하며 그 합계와 최종 복호화 증명을 검사해야 한다. 키 보관자는 임의 부분합·개인 표를 복호화하지 않도록 고정된 최종 집계에 요청을 결합해야 한다. 정족수 공모의 한계도 공개한다.

### S7. 검증 상태·성능·외부 앵커

단일 VALID 대신 개인 포함·과거 연결·규칙 유효성·집계·자격·의도 검사·최초 앵커 확인을 나눈다. PROOF_UNAVAILABLE과 유효 서명 자료의 실제 충돌을 분리하고, 기한 경과도 명시한다.

3~5천 건 경계·CPU 80%·3초 등 추가 수치도 실측 전에는 예시 목표이지 사실이 아니다. 작은 격리 시험으로 자료·단말별 측정을 한 뒤 머클·배치를 선택한다. 독립 사본은 통제 주체·보존 정책으로 판단하며 URL 개수로 보장하지 않는다.

### S8. 남은 운영 결정

독립 집계 키 보관 주체와 정족수, 자격 등록 정책, 악성 JS 위험의 수용 여부, 공개 결과의 소수 참여 정책은 아직 확정되지 않았다. 집계 키 의식·독립 보관자 참여가 필요하면 완전 무인 운영과 충돌할 수 있으므로 숨기지 않는다. 모든 개인 평문 표를 공개하는 현 정책은 B-1과 양립하지 않아 신규 모드에서 바꾸는 방향이며 제품 변경 승인·실증은 아직이다.

문서가 B-1을 기준으로 정리됐다고 해서 이 항목들이 해결됐거나 구현 착수가 승인됐다는 뜻은 아니다. 실제 유지되는 프로토콜/라이브러리 선정과 독립 검토가 먼저다.

## 6. v0.5 재검토 두 건의 판정 — v0.6 반영

출처는 사용자가 후속 대화로 전달한 1~7번 검토와 H1~H8 검토다. [격리 실험 계획](ledger-witness-poc-plan-2026-10-28.md)에 공식 확인 사실·미결 사항·공격 벡터를 분리했다.

### T1. 기존 시스템 우선 평가 — 수용

Belenios의 역할 분리·이벤트 체인·서명 자격·원래 검증 도구를 먼저 평가한다. 이미 체인이 있으므로 중복 원장을 새로 만드는 방향은 보류한다. 기존 엔진에 원래 없는 서명 확인증이나 복호화 정책을 있다고 가정하지 않는다. 공식 검증기 호출과 독립 암호 구현 교차 검증도 구분한다.

### T2. 버전·라이선스 사실 확인

2026-10-28 공식 배포 목록과 원격 ref에서 Belenios 3.3.0 및 stable 대상 커밋을 확인했다. 옛 .org 자료와 일부 패키지 정보는 최신 소스 판단 근거가 되지 못한다. 개발 기록의 4.0.0(dev) 추가 암호 변경과 안정판에 대한 영향은 채택 전 확인 관문으로 남긴다. AGPL 의무는 실제 결합/수정 방식으로 검토하고 서비스 분리만으로 예외라고 하지 않는다.

ElectionGuard C 공식 저장소의 archive 표시는 확인했다. 이를 전체 계열의 현재 유지 중단이나 모든 대체 구현 부재로 확대하지 않는다. ‘Wasm이면 형식 검증됨’, ‘브라우저 라이브러리는 전혀 없음’ 같은 포괄적 주장은 채택하지 않는다.

### T3. 범위 통제 — 수용

첫 신규 B-1 격리 실험은 단일·다중·항목별 찬반만 다룬다. Borda의 수학적 불가능성·특정 기기 연산 불능을 확인한 것이 아니라 실제 지원과 성능이 검증되지 않아 범위를 좁힌 결정이다. 기존 rank 기능 삭제·새 평문 경로 출시 결정은 아니다.

H6의 `q[min]+A=1` 단일식은 기권 시 모든 선택이 0이라는 다른 조건 없이 충분하지 않다. min=2, q=[1,0], A=1이면 식을 만족하면서 기권자가 1개 순위를 선택한다. 원래의 `A=1 → m=0` 조건을 유지해야 한다. 후속 순위 검토에 남긴다.

### T4. 투표 복사 공격 — 추가 필수 벡터 수용

다른 자격으로 암호문/증명 복사, 재서명, 재무작위화 후 증명 재사용, 다른 선거 컨텍스트 재사용을 시험한다. 필요한 결합은 선택 프로토콜의 원래 명세·코드로 확인하고 Fiat–Shamir 입력을 임의로 새로 추가하지 않는다. 별개 정상 유권자가 같은 후보를 새 난수로 선택하는 것은 금지할 일이 아니다.

### T5. 독립 보관자 도구·복호화 오라클 — 수용

모아이 서버가 제공하는 웹 페이지에 비밀 지분을 입력시키는 운영 형태는 B-1의 독립 키 목표와 맞지 않는다. 고정된 독립 도구가 원래 기록·자격·유효성·최종 집계 대상을 재검산해야 한다. 각 도구가 서버의 다른 분기를 최종본으로 받아들이지 않도록 공통 앵커의 일치도 확인해야 한다.

‘선거당 호출 한 번’ 대신 ‘승인된 하나의 최종 대상에만’ 복호화를 허용한다. 같은 대상의 통신 재시도를 막으면 가용성을 해친다. 다른 대상·부분합·개인 표·분기 대상 요청을 거부하고 재시작 후에도 결정이 유지되는지 시험한다. 정족수 이상 공모 위험은 남는다.

### T6. 재투표·상태 기계 — 엔진 정책 확인 후 반영

기존 Belenios 명세의 마지막 표 집계는 모아이의 한 번 소비 정책과 다르다. PoC는 원래 정책을 측정하며 제품 선택은 미결로 둔다. 버튼만 숨겨 재투표를 막았다고 하지 않는다. 전체 이벤트 수·Ballot 이벤트 수·최종 유효표 수를 구분한다.

응답 유실 시 공개 이벤트·서명만 다시 받아 확인증을 구성할 수 있게 평가한다. 원형 tracker에 서버 서명이 있는지는 별도 확인한다. 개인 난수·자격 분실 복구를 추가하지 않는다.

### T7. 웹 보호·기표 의도 — 부분 수용

CSP·SRI·재현 가능한 빌드·배포 자료 대조를 방어층으로 검토한다. 운영자가 HTML·헤더·클라이언트를 함께 바꾸는 공격을 막는 독립 신뢰점으로 자동 간주하지 않는다. PWA·네이티브·앱스토어라는 이름만으로 배포 신뢰가 사라지지 않는다. 의도 검사도 평문 유출 방지와 구분한다.

### T8. 실험과 출시의 구분

가상 데이터·가상 자격·격리 서비스에서 원형 엔진을 평가할 계획만 작성했다. 운영 DB 쓰기·실제 문자·외부 공개·라이브러리 설치·서비스 기동은 수행하지 않았다. PoC 결과·보안 검토·역할 운영 주체·라이선스·재투표/공개 하한 정책 확인 전에는 실제 채택·출시 판정을 내리지 않는다.

## 7. v0.7 — 후속 검토와 선택형 문자 인증

### U1. 사용자가 결정한 제품 정책

중요한 투표에서 생성자가 **‘기표 직전 휴대폰 문자 인증 필수’**를 선택할 수 있도록 설계했다. 기본값은 해제이고 기존 기본 인증은 유지한다. 필수 선거는 정확한 제출 기표문에 결합된 새 휴대폰 인증을 실제 접수 경계에서 검사한다. 정책은 시작 전에 고정한다. 재시도·동시 요청·마감·발송 실패 조건은 설계안 §6.1과 PoC O01~O07에 명시했다. 현재는 문서 변경이며 기능 구현·실제 문자 발송은 하지 않았다.

### U2. 독립 자격과 추가 인증의 경계

문자 OTP는 휴대폰 소지 확인을 강화하지만 독립 투표 자격이 아니다. 비밀 자격을 모아이 또는 공용 문자 발송 경로에 실으면 운영자가 자격을 획득할 수 있다는 지적을 수용한다. 독립 발급·별도 전달 경로와 공개 자격 목록 대조가 필요하다. 같은 통제 주체의 별도 도메인·계정·데몬만으로 독립성이 성립하지 않는다. 자격 폐기 시점은 수신 확인·복구 불가 정책·백업까지 함께 검토한다.

### U3. 원형 tracker와 추가 서명의 구별

후속 검토의 핵심은 원형 tracker에 서버 접수 서명이 없다는 점이다. ‘원형 서명을 그대로 추출하면 된다’는 개선안은 실제 서명 필드의 존재를 확인하기 전에는 채택할 수 없다. 얇은 어댑터가 필요하면 원형의 실제 Ballot 이벤트와 head를 확인한 뒤 **모아이 발급자의 별도 서명**으로 증언한다. 원형 검증·외부 보존 사본과의 연결은 각각 검사하며 새 체인을 임의로 중복 생성하지 않는다.

### U4. 버전·재투표·보관자·기권 검토

3.3.0/개발판의 암호 변경 영향과 Single/Pedersen 구성의 차이는 고정 소스 diff 및 실제 시험 대상으로 남긴다. 여러 Single이 모든 보안 문제를 회피한다고 판정하지 않는다. 유지관리자 확인은 후보 관문이며 이번 작업에서 문의를 보내지 않았다.

재투표 거부 설정·직접 접수 경로와 공개 Ballot 이력의 별도 정책 검사를 함께 평가한다. 공개 자격 삭제로 과거 검증을 깨뜨리지 않으며 동일 기표문 재시도와 다른 기표문의 재투표를 구분한다. 보관자는 공통 최종 앵커를 독립 경로로 대조한 뒤 같은 대상만 승인한다. 서로 다른 해시를 지분에 써 넣기만 하면 분기 합의가 해결되거나 복호화가 자동 실패한다고 가정하지 않는다.

질문 단위 blank와 투표지 전체 기권의 차이를 표로 검토한다. 정확히 표현하지 못하는 설정은 신규 B-1 지원 대상에 넣지 않는다. Borda는 계속 보류하며 기권이면 모든 선택이 0이라는 조건을 유지한다.

### U5. 증거·측정·라이선스의 과장 방지

공식 도구 래핑, 독립 포맷 파서, 독립 암호 검증기의 범위를 구분한다. 임의 성능 수치나 후보 라이브러리 이름을 안전성 근거로 쓰지 않는다. 실제 단말·입력별 측정 전에 UX 목표를 고정한다. AGPL의 정확한 예외 문구·수정·배포·결합 형태는 별도 검토하며, 단순 API 분리로 면제되거나 모아이 전체 공개가 자동 확정된다고 판단하지 않는다.
