# 재검토 의뢰서 — B-1 기존 엔진 평가와 격리 실험 범위

> **최신 확정 계획:** [v1.0 기존 서비스 기반 경량 감사 계획](voting-native-audit-plan-2026-10-28.md)이 우선한다. Belenios 도입과 운영자 비신뢰 B-1 연구는 보류하고, 기존 모아이에 표준 해시·서명·숨김 약정·공개 집계 재검증을 추가한다. 아래는 과거 검토 기록이며 현재 구현 완료를 뜻하지 않는다.

- 개정: 2026-10-28, v0.7
- 자료: [설계안](ledger-witness-design-2026-10-28.md), [격리 실험 계획](ledger-witness-poc-plan-2026-10-28.md), [검토 반영·정정 기록](ledger-witness-review-resolution-2026-10-28.md)
- 목적: 자체 암호 조립 대신 기존 시스템을 사용하는 실험 범위가 적절한지 검토한다. 구현·운영 배포·외부 전송 요청은 아니다.

## 배경

모아이투표는 문자 링크/코드로 참여하는 웹 서비스다. 현재는 인증 토큰과 평문 선택을 함께 받으며 명부와 투표지를 별도로 저장한다. 새 목표는 운영자 혼자 개인 선택을 복호화하지 못하고, 참여자 보관 확인증·공개 원장·독립 검증으로 기록 변경과 집계를 확인하게 하는 B-1이다.

B-1도 악성 기표 JS의 암호화 전 유출, 자격 발급자와 운영자의 공모, 복호화 정족수 공모, 결과 자체의 소수 참여 추론을 자동 해결하지 않는다. 별도 분쟁 개인정보 보관소·복구 키·합의 네트워크·화폐는 범위 밖이다.

최근 검토는 기존 엔진을 우선 평가하고 복사 공격·독립 보관자 도구를 추가 검토하라고 권고했다. 이에 Belenios를 우선 후보로 삼고 첫 실험은 단일·다중·항목별 찬반으로 한정했다. Borda는 신규 B-1 실험에서 보류하되 기존 기능을 삭제하지 않는다.

공식 자료에서 기존 Belenios 이벤트 체인·역할 분리·원래 검증 도구·재투표 정책과 최신 배포 정보를 확인했다. **설치·실행·공격 시험은 아직 하지 않았다.** 3.3.0 확인만으로 채택하거나 안전성을 승인하지 않으며 개발 기록의 추가 암호 수정 영향을 먼저 확인한다.

## 우선 검토 질문

1. 선택할 실제 버전·커밋과 공개 보안 변경을 검토하면 P0 적합성 관문을 통과할 수 있는가? 3.0 명세와 3.3 구현·개발판 차이를 무엇으로 검증해야 하는가?
2. 기존 엔진과 원래 체인·tracker를 그대로 쓰고 모아이는 안내/연결 계층만 맡는 방식이 목표에 맞는가? 별도 체인이 꼭 필요한가?
3. 원래 tracker가 증명하는 것과 모아이의 서명된 과거 기준점 요구 사이에 무엇이 빠져 있는가? 최소 어댑터의 신뢰 경계는 어디인가?
4. C01~C06 복사·다른 자격 재사용·재무작위화·재시도 벡터가 충분한가? 동일한 정상 선택을 오탐하지 않는가?
5. 자격 생성·전달을 모아이 운영자 밖으로 분리할 실제 역할과 경로는 무엇인가? 같은 발송 시스템·로그·키 접근 때문에 실질적으로 다시 합쳐지지 않는가?
6. 보관자 도구가 독립적으로 같은 최종 데이터를 고정·재집계하는지 무엇으로 확인하는가? 다른 분기·부분합·개인 표·재시작·같은 대상 재시도에 대한 D01~D05를 평가해 달라.
7. 원래 재투표 정책과 현재 모아이 1인 1회 정책을 어떻게 다룰 것인가? UI에서 숨기는 수준을 넘는 지원/수정 범위와 검증 부담을 밝혀 달라.
8. 단일·다중·항목별 찬반의 기권·최소 선택 규칙이 원래 엔진 형식과 같은가? 다르면 원형 규칙을 임의 변경하지 않고 어떤 제약으로 평가해야 하는가?
9. 원래 검증기 호출·같은 코어 사용과 진짜 독립 구현 교차 검증을 보고서에서 정확히 구분했는가?
10. AGPL, 엔진과 모아이의 결합, 수정 도구 배포·소스 제공의 검토 범위를 제시해 달라. 서비스 분리를 곧 라이선스 면제로 단정하지 말아 달라.
11. 실제 기기·후보 수·표 수·증명·파일 규격에 맞는 최소 측정과 UX 중단 기준은 무엇인가? 미측정 3초·CPU 80% 등을 보장으로 삼지 말아 달라.
12. Borda는 후속 검토용이다. 기권 비트 제약의 반례와 연속 순위 조건을 검토하되, 그 작업 때문에 첫 실험을 자체 암호 개발로 확대하지 말아 달라.

## 원하는 산출물

### 추가 요청: 선택형 기표 직전 문자 인증

생성자가 ‘기표 직전 휴대폰 문자 인증 필수’를 선택하면 최종 제출 때 등록 휴대폰의 새 OTP와 독립 투표 자격을 모두 요구하는 정책을 추가했다(설계안 §6.1, PoC O01~O07). 기본값 해제이며 해제해도 기존 기본 인증은 유지한다. 현재는 문서 설계이며 실제 발송·구현은 하지 않았다.

추가로 확인해 달라: 엔진 직접 호출까지 필수 인증을 강제할 수 있는가? 선거·주체·정확한 암호문에 승인 결합과 1회 소비가 가능한가? 응답 유실 후 같은 표 조회에 재인증/재발송을 강요하지 않는가? 자격 발급·전달과 모아이 문자 경로가 다시 합쳐지지 않는가? 문자 인증으로 해결하지 못하는 운영자 도용·SIM 탈취·악성 웹 JS 위험을 정확히 구분했는가?

### 제출 형식

각 항목에 문제·공격 순서·필요 권한·최소 개선·검증 방법·실제 확인한 소스/버전을 적어 달라. 다음 세 판정을 구분해 달라.

- P0 자료 조사 후 격리 실행을 시작할 수 있는가?
- 원형 엔진 실험이 통과해도 통합 전에 무엇을 결정해야 하는가?
- 제품 채택·출시 전에 어떤 보안·운영·라이선스 조건이 남는가?

‘기존 시스템 사용’, ‘Rust/Wasm 사용’, ‘형식 검증 논문 있음’이 곧 실제 버전과 전체 통합의 안전성을 보장한다고 하지 말아 달라. 실제 명부·개인 영수증·비밀키를 요구하거나 전송하지 말고, 합성 자료와 공개 문서로 먼저 검토해 달라.
